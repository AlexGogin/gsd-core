**The idle/staleness detector now fires when `last_activity` carries a description** — a `last_activity` written in the shape `templates/state.md` prescribes (`[YYYY-MM-DD] — [What happened]`) parsed to `NaN`, and because the detector treats an unparseable value as "not stale" it failed open to `false`. Any project whose `last_activity` kept its description was never reported idle, no matter how long it had sat. The leading date is now parsed out of the value, so the description no longer blinds the only staleness signal in the front door. An impossible calendar date such as `2026-02-30` is now rejected outright rather than silently rolling forward to a real — and wrong — date. Two further defects found in review are fixed alongside it: a `last_activity` carrying a timezone NAME (`2026-07-28 23:30:00 GMT`) is now read as the instant it names on every host, where before the same value could resolve hours apart depending on the host's UTC offset and on whether a `T` or a space separated the time — and an abbreviation that is not exactly UTC (`EST`, `CEST`) degrades to no-signal instead of a guess; and a real year below 100 (`0099-06-15`) is no longer rejected as an impossible date by the calendar guard. (#2570)
